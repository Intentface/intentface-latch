title: Turn inputs
description: Principal, context, and the three views of a message — what flows into a turn and what comes back out.
---

Three things decide what a turn sees: **who** is asking (principal), **what world** they're in (context), and **which messages** the model gets (projections).

## Principal — identity, opaque by design

`Principal` is your type. Latch never inspects it, and there is no built-in notion of a user, an org or a role.

```ts
interface Principal {
  orgId: string;
  userId?: string;
}
```

You resolve it however you authenticate (`ContextResolver`), and the storage adapter derives an **owner key** from it — that key is what scopes every row.

```ts
const owner = (p: Principal) => (p.userId ? [p.orgId, p.userId] : [p.orgId]);
```

Two consequences worth internalising:

- **Authorization is yours.** Latch enforces isolation by owner key at the storage layer; it does not decide whether this user may use that agent.
- **Identity must be stable.** The principal is serialized onto the run as an opaque `identity` blob so a resumed or cron-fired turn can rebuild it via `reconstructPrincipal`.

<Callout type="warn" title="Pin the tenant at session creation">
If the value your owner key derives from can change mid-session — an "active org" the user can switch — then owner-keyed rows fragment silently: yesterday's chats belong to a key you no longer produce. Resolve it once when the session is created and keep it stable for the session's life.
</Callout>

## Context — the world the agent runs in

`defineContext` declares the shape once and builds it per turn. Every tool receives it — plus `principal`, the current `run`, and the `writer` — as `options.context`, so anything a tool needs per tenant (endpoint, plan tier, feature flags) goes in here, and a secret is resolved by the tool from the principal (see [how a principal reaches a tool](/docs/foundations/principals#how-a-principal-reaches-a-tool)).

```ts
import { defineContext } from "@intentface/latch-core";

const context = defineContext<Principal, Ctx>({
  build: async ({ principal }) => ({
    orgId: principal.orgId,
    orgName: await lookupOrgName(principal.orgId),
  }),
});
```

The type then flows into `defineAgent`, tools and hooks with no `any`.

<Callout type="warn" title="turnContext is ephemeral — derive from the principal">
`build` also receives `turnContext`: the per-turn request payload (parsed body, active document, UI selection). It is **never persisted with the run**, so a resumed or scheduled turn rebuilds context *without it*. Anything durable must derive from the principal. Reading identity out of `turnContext` produces a turn that works interactively and breaks on resume — which is the worst kind of bug, because it only appears after a crash.
</Callout>

## Messages — one record, three views

`AppMessage` is just an AI SDK `UIMessage` typed with Latch's metadata. It is the source of truth; everything else is a projection.

```ts
type AppMessage = UIMessage<AppMetadata, UIDataTypes, TOOLS>;

interface AppMetadata {
  visibility?: "user" | "internal" | "redacted"; // client-projection axis
  sendToModel?: boolean; // model-projection axis
  model?: string;
  usage?: {
    inputTokens?: number;
    outputTokens?: number;
    cacheReadTokens?: number;
    cacheWriteTokens?: number;
  };
  cost?: number;
  finishReason?: string;
  createdAt?: number;
  voice?: { durationMs: number };
}
```

The **two axes** are the whole mechanism:

| | `visibility` | `sendToModel` |
| --- | --- | --- |
| Governs | what the *user* sees | what the *model* sees |
| Applied by | `toClientMessages` | `toModelMessages` |

So a compaction summary or an injected instruction can reach the model without ever appearing in the conversation, and a redacted message can stay in the record while being invisible to both.

```ts
import { toClientMessages, toModelMessages } from "@intentface/latch-core";

const forUser = toClientMessages(stored); // drops internal + redacted
const forModel = await toModelMessages(stored, { tools }); // drops sendToModel: false
```

<Callout title="Pass the same tools to both">
`toModelMessages` wraps the SDK's `convertToModelMessages`, which consults each tool's `toModelOutput` to decide what a tool result looks like to the model. Pass the same tool set you passed to the agent, or replayed history won't match what the model saw live.
</Callout>

`toModelMessages` also, in order: cuts to the live context window at the compaction boundary, drops `sendToModel: false`, neutralizes audio file parts, and closes any dangling tool calls (a tool call with no result makes conversion throw).

## Compaction

A chat that never ends — a DM, a months-old thread — would grow its prompt forever. `runtime.compactChat` summarises the history and appends a **boundary marker** (`data-compaction`); from then on the model projection starts at that boundary and reads the summary instead of the turns it replaced.

```ts
const result = await runtime.compactChat({
  chatId,
  principal,
  focus: "keep the training plan",
});
// → { summary, compacted } | null
```

Stored history is untouched — compaction shrinks the *projection*, never the record. `null` means there was too little to compact. It throws `PendingApprovalError` if the last turn is paused awaiting a human.
