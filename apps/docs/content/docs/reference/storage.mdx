Storage is the only required seam with real behavioural obligations. `@intentface/latch-drizzle` implements it for Postgres and SQLite; this page is what you need if you're writing another one, or debugging one.

```ts
createRuntime({ storage, context, agents });
```

## What it stores

Five record types. The adapter owns the **owner key** — an opaque string it derives from the principal — and every method that *takes a principal* scopes its read by it. A few internal methods take a bare id instead (`getRun`, `reclaimRun`, `reapExpiredRuns`); those are runtime machinery, not a caller-facing API, and they are **not** ownership-scoped. Reach for the [Runtime operations](/docs/runtime) rather than the adapter when you're serving a request.

| Record | Holds |
| --- | --- |
| `ChatRecord` | id, owner, agent, title, `kind`, timestamps |
| `RunRecord` | status, identity blob, lease fields, attempt count, token usage, cost, error, the agent version it ran |
| `RunLease` | `{ owner, fencingToken }` — proof of single-writer ownership |
| `UsageRecord` | per-run token/cost row for billing rollups |
| `ScheduleRecord` | cron, timezone, prompt, opaque `delivery`, `nextRunAt`, lease fields |

Two fields are **opaque and must round-trip byte-for-byte**: `RunRecord.identity` (the serialized principal) and `ScheduleRecord.delivery` (the host's delivery target). Core never interprets either.

`RunRecord.agentVersion` is the stored agent-record version this run started on (null for code-declared agents, which have no stored record). It is written when the run is **opened**, not when it settles: a run that errors or crashes never reaches a terminal update, and "which version produced these failures" is exactly the question worth answering. It stays fixed across a resume.

`ChatRecord.kind` is an open vocabulary: `"user"` for conversations, `"internal"` for runtime-created sub-threads (the `sub_…` chats `spawn_agent` mints). `listChats(principal, { kind: "user" })` is how a sidebar hides the machinery.

## The methods

```ts
interface StorageAdapter<P> {
  // Chats
  createChat, getChat, listChats
  // Messages
  loadMessages, appendMessages
  // Runs
  createRun, updateRun, getRun, listRuns
  // Durability
  claimRun, heartbeatRun, reclaimRun, reapExpiredRuns
  // Usage
  recordUsage
  // Schedules
  createSchedule, listSchedules, deleteSchedule, bumpSchedule,
  claimDueSchedules, completeSchedule
}
```

## Guarantees you must provide

These are what make the runtime safe on multiple nodes. Getting them wrong produces bugs that only appear under concurrency — the expensive kind.

### Claims are atomic and exactly-once

`claimRun`, `reclaimRun` and `claimDueSchedules` must be **single atomic transitions** (one conditional `UPDATE … WHERE`), not read-then-write. Every node's cron fires `sweep()` and `runDue()` concurrently; correctness comes entirely from the database refusing the second claimant.

Get this wrong and you get double-fired schedules and two workers streaming into the same run.

### Fencing tokens gate stale writers

`RunLease` carries a monotonic `fencingToken`, bumped on every claim. Guarded writes must land **only** if `(owner, fencingToken)` still match the row.

The scenario: a worker's lease expires (it was slow, not dead), the reaper reassigns the run, and then the original worker wakes up and tries to write. Without fencing it overwrites newer state. This is why the token exists and why it must be checked in the `WHERE` clause, not in application code.

### A schedule consume reports whether it applied

`claimDueSchedules` stamps a lease that is never renewed, so a slow pass can lose its claim before it consumes the occurrence — to another node, or to a later `runDue` pass on the same instance (same owner id). `completeSchedule` is the write that settles which claimant fires:

- Fence it on `owner` **and** on `claim.leaseExpiresAt` when given — the expiry that claim stamped, which is strictly later on every re-claim, so it tells two claims by the same owner apart.
- Return `false` when the fence rejected the write. The runtime then does not fire; the current holder owns the occurrence.

Returning `void` is still accepted and treated as applied, so older adapters keep working — but they keep the duplicate-fire window this closes.

### Ownership scoping is not optional

Every read that **takes a principal** must filter by the derived owner key — `listChats`, `loadMessages`, `listRuns`, `listSchedules`. Filter in the query, not after it: a capped scan that slices in application code silently stops being correct once a tenant has more rows than the cap.

`getRun(id)` takes no principal and is deliberately unscoped — the reaper and resume path look runs up by id alone. Never serve it straight to a caller; go through `Runtime.getRun`, which scopes the lookup for you.

### Chat id collisions surface as a conflict

`createChat` must throw `ChatConflictError` when the id exists. Clients supply chat ids, so a caller can collide with a chat they don't own: the scoped `getChat` misses, and the insert races into the primary key. The typed error is what lets the HTTP layer answer `409` instead of `500`.

```ts
import { ChatConflictError } from "@intentface/latch-core";

try {
  await storage.createChat(principal, { agent, id });
} catch (error) {
  if (error instanceof ChatConflictError) return new Response(null, { status: 409 });
  throw error;
}
```

### Messages append, never mutate

`appendMessages` is the write path. Approval decisions, tool results and compaction boundaries are all recorded as appended message state — the log is the source of truth, and history is not rewritten in place.

**One active run per chat.** `createRun` and `claimRun` throw `ChatBusyError` (code `chat_busy`) when the chat already has a live active run — a lease that hasn't expired, or for non-durable runs an active row younger than the adapter's stale timeout. An expired one is superseded first (marked errored, fencing token bumped), so a crashed turn never blocks its chat. The shipped adapters enforce this with a partial unique index on `(chat_id) WHERE status = 'active'`, so it holds under concurrency, not just in the happy path. `reclaimRun` returns null for a run whose chat has since started a newer active run. `openTurn` (implemented by the shipped adapters) opens the run and appends the user message in one transaction, so a refused turn persists nothing and a crash can't leave a run without its message. It is optional in the type for compatibility, but **a durable adapter must implement it**: without it a turn opens as two writes, and a process that dies between them leaves a run whose own message never landed — crash recovery then reads the previous turn's tail as that run's history. The runtime warns at startup when durability is on and `openTurn` is missing. This is what keeps two tabs, a webhook retry racing a reply, or a schedule firing mid-conversation from interleaving one history.

## Using the shipped adapter

```ts
import { createSqliteAdapter, migrate, schema } from "@intentface/latch-drizzle";
import { createClient } from "@libsql/client";
import { drizzle } from "drizzle-orm/libsql";

const client = createClient({ url: "file:local.db" });
const db = drizzle(client, { schema });

// `migrate` executes DDL, so it takes the libSQL client — not the drizzle db.
await migrate(client);

const storage = createSqliteAdapter(db, { owner });
```

The adapter takes the db, not a connection string — your app owns the connection and the pool. Tables are prefixed `latch_*`, and the package ships the migrations; consume those rather than hand-declaring the schema in your own migration folder.

<Callout title="A concurrency test is worth more than a unit test here">
The failure modes above are invisible to single-threaded tests. `apps/example/src/durability.smoke.ts` and `resume.smoke.ts` exercise claim, heartbeat, reap and resume against a real database; point them at a new adapter before trusting it.
</Callout>
