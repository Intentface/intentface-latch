**The principal says who is asking. The context is what that person's tools receive.** Both are your own types; Latch never interprets them, it carries them everywhere.

## Why they exist

Every read, write and tool call in a multi-customer product needs to know whose data it's touching. That includes runs where nobody is logged in: a schedule firing at 9:00, a crashed answer resuming at 3:00. Latch carries the principal through all of them, so nothing has to be passed around by hand.

## The principal

A small object, built by your route from your login:

```ts
type Principal = { orgId: string; userId: string };

runtime.handleChat({ agent, chatId, message, principal: { orgId: user.orgId, userId: user.id } });
```

Keep it to plain ids. It's saved with every run and schedule, so background work knows whom it's acting for. Anything that can change (names, plans, permissions) belongs in the context.

## The context

Built fresh on every turn from the principal, and handed to every tool:

```ts
const context = defineContext<Principal, Ctx>({
  build: async ({ principal }) => ({
    orders: ordersFor(principal.orgId), // already bound to this customer
    plan: await planOf(principal.orgId),
  }),
});

const find_order = tool({
  description: "Find an order",
  inputSchema: z.object({ id: z.string() }),
  execute: async ({ id }, { context }) => (context as Ctx).orders.get(id),
});
```

Because the context is rebuilt from ids, a scheduled or resumed run gets the same, current values, even with no request.

## Why two things

They live for different lengths of time.

|  | Principal | Context |
| --- | --- | --- |
| What | Who is asking | What their tools work with |
| Built by | Your route, from your login | `build`, from the principal |
| Lifetime | Saved with every chat, run and schedule | One turn, never saved |
| Holds | Plain ids | Anything: clients, plans, permissions, keys |
| Changes | Never, for a given person | Every turn, reading current values |

Put a plan in the principal, and it's frozen into every run and schedule: someone who upgrades keeps their old plan on last month's report. Use only the principal, and every tool looks things up itself and has to remember to filter by customer. Splitting them means looking up once, fresh, on every turn, and handing tools objects already bound to the right customer.

The agent itself can be built from the context too, so each plan gets its own model and tools, decided again on every turn ([limits per plan](/docs/guides/plans-and-limits) work the same way):

```ts
const support = defineAgent<Principal, Ctx>(({ context }) => ({
  model: context.plan === "pro"
    ? anthropic("claude-sonnet-4-6")
    : anthropic("claude-haiku-4-5"),
  instructions: "You help customers with their orders.",
  // Free plans can look orders up; only Pro can refund from chat.
  tools: context.plan === "pro" ? { find_order, refund } : { find_order },
  toolApproval: { refund: "user-approval" },
}));
```

The rule of thumb: **ids in the principal, everything you look up in the context.**
